# Agent Skill Evaluation and Selection for the CRC Python Refactor

## Context and Evaluation Criteria

`cloud-resource-cleanup` (`crc.py` and `crc/**`) is a synchronous Python CLI tool run by Jenkins to stop and delete leftover cloud resources across AWS, Azure, GCP, and OCI. The upcoming in-place refactor targets:

- Provider and resource cleaner self-registration via decorators.
- A structural `Cleaner` protocol separating read-only `plan()` from destructive `apply()`.
- A central, pure policy module for tag (`--filter_tags`, `--exception_tags`, `--notags`), age (`--age`, `--detach_age`, `--custom_age_tag_key`, `--max_age`), and regex (`--name_regex`, `--exception_regex`) filtering.
- Architectural boundaries enforced via `import-linter` contracts.
- Mechanical guardrails via `ruff` (including `UP` and `FURB` modernisation rules) and strict static type checking (`mypy` / `pyright`).
- Per-package `README.md` files and preservation of all existing unit tests (`tests/`) and destructive-cleanup invariants documented in `CLEANUP_SAFETY.md`.

Five candidate skills from MCP Market (and their linked GitHub source repositories, `SKILL.md` files, and companion reference files) were read and evaluated against these requirements.

## 2. Recommendation: Adopt, Merge, or Drop

### Summary Decision

- **Adopt as-is**: **None (0 of 5)**
- **Merge into a combined CRC Python skill (with role-scoped views)**: **Skills 1, 3, 4, and 5** (`python-patterns`, `python-error-handling`, `python-type-safety`, `python-anti-patterns`)
- **Drop**: **Skill 2** (`python-testing-patterns`)

### Rationale

1. **Why none can be adopted as-is**:
   - Every one of the five skills recommends patterns or third-party libraries that conflict with this refactor: Skills 1, 2, 4, and 5 promote `async`/`await`; Skills 3, 4, and 5 promote `pydantic` / `pydantic-settings` and `httpx`; Skill 2 promotes `sqlalchemy`, `hypothesis`, and `pytest-asyncio`.
   - More importantly, Skills 3 and 5 teach a blanket batch-processing rule ("never let one bad item abort a batch; return a `BatchResult` of succeeded/failed items") that directly threatens `CLEANUP_SAFETY.md` invariants if followed blindly by an coding agent (such as the `aws`+`disk` opt-in circuit breaker, region-list auth failure re-raises, fail-closed skipping on incomplete CloudWatch pagination or malformed retention tags, and aborting spot instance termination when spot request cancellation fails).

2. **Why Skill 2 (`python-testing-patterns`) should be dropped**:
   - Its `SKILL.md` is a 45-line stub containing no technical patterns, and its 906-line `resources/implementation-playbook.md` is ~80% generic tutorial boilerplate (`def add(a, b)`, SQLAlchemy SQLite sessions, `pytest-asyncio`, `hypothesis`, GitHub Actions YAML) while containing zero guidance on mocking cloud SDKs (`boto3`, Azure, GCP, OCI) or testing destructive operation ordering. The 4 useful pytest patterns it mentions (`@pytest.mark.parametrize`, `pytest.raises(..., match=...)`, `monkeypatch`, `tmp_path`) can be expressed in 15 lines inside the merged skill.

3. **Why Skills 1, 3, 4, and 5 should be merged**:
   - Skills 3, 4, and 5 come from the same upstream plugin (`wshobson/agents/plugins/python-development/skills/*`) and heavily duplicate one another, while Skill 1 overlaps with Skill 4 on `Protocol`, generics, and unions and with Skill 3 on custom exceptions. Merging their relevant sections into a single project-tailored skill eliminates redundancy, strips conflicting dependencies (`pydantic`, `async`, `Result[T, E]`), and aligns error-handling and review rules with `CLEANUP_SAFETY.md`.

## 3. Overlaps and Refactor Gaps Across the Five Skills

### Overlaps Between the Candidate Skills

- **Structural typing with `typing.Protocol`**: Covered in Skill 1 (`## Protocol (Duck Typing)`) and Skill 4 (`### 3. Protocols` and `references/details.md` Patterns 7–8).
- **Modern Union syntax (`T | None`) & Generics (`TypeVar`, `Generic`, parameterized collections)**: Covered in Skill 1 (`## Type Hints`), Skill 4 (`### Pattern 2`, `### Pattern 4`, `references/details.md` Patterns 5–6), and Skill 5 (`## Type Safety Anti-Patterns`).
- **Exception hierarchies & exception chaining (`raise ... from e`)**: Covered in Skill 1 (`## Error Handling`), Skill 3 (`### 4. Preserve Context`, `references/details.md` Patterns 5–6), and Skill 5 (`### Bare Exception Handling`).
- **Batch partial-failure handling (`BatchResult` dataclass with `succeeded`/`failed` dicts)**: Duplicated nearly verbatim between Skill 3 (`references/details.md` Pattern 7) and Skill 5 (`### Ignored Partial Failures`).
- **Early boundary input validation & Pydantic models**: Duplicated between Skill 3 (Patterns 1–3) and Skill 5 (`### Missing Input Validation`).
- **Separating pure business logic from I/O & not leaking internal SDK/ORM models**: Covered in Skill 1 (`## Dataclasses as DTOs`, `## Package Organization`), Skill 4 (`references/details.md` Pattern 5), and Skill 5 (`## Architecture Anti-Patterns`).
- **Context managers (`with`) for resource cleanup**: Covered in Skill 1 (`## Context Managers`) and Skill 5 (`### Unclosed Resources`).

### Gaps Not Covered by Any of the Five Skills

None of the five skills cover the following CRC-specific refactor requirements, which must be authored directly into our project skill/guardrails:

1. **Decorator-based provider & cleaner self-registration**: Registering cloud resource cleaners via a typed decorator (e.g., `@register_cleaner(cloud="aws", resource="disk")`) without import-time side effects, global mutable singleton traps, or circular imports.
2. **`Cleaner` protocol with read-only `plan()` and `apply()` separation**: Enforcing that `plan()` performs discovery and policy filtering with zero mutating cloud API calls (backing `--dry_run`), while `apply()` executes state-changing cloud calls (`delete`, `stop`, `cancel`, tag mutations) on planned items.
3. **Central policy module (`crc/policy`) & fail-closed safety invariants**: Pure evaluation of `--filter_tags`, `--exception_tags`, `--notags`, `--name_regex`, `--exception_regex`, `--age`, `--detach_age`, `--custom_age_tag_key`, and `--max_age`, strictly preserving `CLEANUP_SAFETY.md` rules:
   - Requiring positive age gates where mandated (`require_positive_age`) and rejecting unknown keys or zero durations (`_normalize_age`).
   - Failing closed (skipping the resource on `ValueError`/`TypeError`/`OverflowError`) when a custom retention age tag is present but empty, unparseable, invalid, or zero (`validated_retention_age`).
   - Ensuring `--max_age` / `MAX_AGE` never silently shortens a floor established by another flag such as AWS `--detach_age`.
   - Failing closed on incomplete or uncertain cloud telemetry (e.g., CloudWatch `GetMetricData` returning non-`Complete` on the final page, truncated pagination, or metric auth errors keeps the EBS volume).
4. **`import-linter` architectural layer contracts**: Defining and enforcing `import-linter` contracts (e.g., `crc.policy` is pure and forbidden from importing provider packages or cloud SDKs; `crc.aws`, `crc.azu`, `crc.gcp`, and `crc.oci` are independent sibling layers that cannot import one another).
5. **Ruff configuration and `UP` / `FURB` modernisation rules**: Enforcing `ruff check` and `ruff format` with pyupgrade (`UP`), refurb (`FURB`), bugbear (`B`), blind-except (`BLE`), and import sorting (`I`) rules.
6. **Mocking cloud SDKs (`boto3`, Azure, GCP, OCI) and verifying destructive call order**: Writing deterministic unit tests without live credentials against `boto3` clients/paginators and `botocore.exceptions.ClientError`/`BotoCoreError`, Azure compute/network clients and LRO pollers (`begin_delete_vm_and_wait`), GCP `InstancesClient`/`DisksClient`/`AddressesClient` and zone operation waits, and OCI `ComputeClient`/`BlockstorageClient` pagination and lifecycle state waits—including asserting strict operation ordering (such as AWS Spot: tag `DeleteOnTermination=false` volumes $\rightarrow$ cancel spot request $\rightarrow$ terminate instance $\rightarrow$ wait for volume `available` $\rightarrow$ delete volume, and rollback/invalidation of `crc_leftover_of` / `crc_leftover_tag_*` tags on cancel/terminate failure).
7. **Per-package `README.md` contracts**: Documenting module responsibilities, opt-in gates, and safety invariants per package and keeping `CLEANUP_SAFETY.md` in sync.

## 4. Proposed Outline for the Merged Skill

We should combine the kept rules from Skills 1, 3, 4, and 5 (plus the core `pytest` mechanics from Skill 2 and the CRC-specific gap rules above) into a single repository-controlled skill bundle consisting of a shared core (`SKILL.md`) and a reviewer checklist (`REVIEW_CHECKLIST.md`).

### Outline of Merged Skill (`crc-python-refactor`)

#### Section 1: Protocols, DTOs, and Registry Decorators *(from Skills 1 & 4 + CRC Gaps)*
- **Rule 1.1 (`Cleaner` Protocol)**: Use `typing.Protocol` (and `@runtime_checkable` only where runtime `isinstance` checks are required) to define the structural `Cleaner` interface with a read-only `plan()` method and a side-effecting `apply()` method.
- **Rule 1.2 (Immutable DTOs)**: Use `@dataclass(frozen=True, slots=True)` with `field(default_factory=...)` for resource descriptors, filter policies, and cleanup plans. Do not introduce `pydantic` or expose raw cloud SDK response dicts/models across module boundaries *(from Skill 1 `Dataclasses as DTOs` & Skill 5 `Exposed Internal Types`)*.
- **Rule 1.3 (Typed Registration Decorators)**: Use `functools.wraps` and `Callable` / `TypeVar` to type provider/cleaner registration decorators (`@register_cleaner(...)`). Never use `@singleton` decorators with hidden mutable state *(from Skills 1 & 4)*.
- **Rule 1.4 (Constructor Dependency Injection)**: Pass cloud SDK clients, policy objects, and loggers into cleaner constructors (or factory methods) so unit tests can inject mocks directly without patching module globals *(from Skill 1 `Constructor Injection`)*.

#### Section 2: Strict Type Safety (`mypy` / `pyright`) *(from Skill 4 & Skill 5)*
- **Rule 2.1 (Public Signature Annotations)**: Annotate every function, method, and class attribute with explicit parameter and return types (`-> None` when returning nothing).
- **Rule 2.2 (Modern Standard-Library Typing)**: Use `T | None` union syntax and builtin generic collections (`list[str]`, `dict[str, list[str]]`, `collections.abc.Sequence`, `collections.abc.Callable`, `collections.abc.Iterator`). Avoid bare `list`, `dict`, or `Any` (restrict `Any` to untyped third-party SDK boundaries and narrow immediately).
- **Rule 2.3 (Type Narrowing with Guards)**: Narrow optional or union values explicitly (`if value is None: ...`) before dereferencing attributes; never use `# type: ignore` to silence unguarded `None` access or custom `Result[T, E]` wrappers.
- **Rule 2.4 (Strict Type-Checker Config)**: Maintain `strict = true`, `warn_return_any = true`, `warn_unused_ignores = true`, and `disallow_untyped_defs = true`, using per-module overrides only as a temporary migration ratchet.

#### Section 3: Pure Policy Separation and Layer Contracts *(from Skills 1 & 5 + CRC Gaps)*
- **Rule 3.1 (Pure Policy vs. Cloud I/O)**: Keep tag, age, and regex filtering pure inside the central policy module (`crc/policy`). Cleaners fetch cloud state and normalize resource metadata into domain DTOs; policy functions take DTOs and return boolean/decision results with zero SDK calls *(from Skill 5 `Mixed I/O and Business Logic`)*.
- **Rule 3.2 (Boundary Parsing)**: Parse and validate CLI arguments, age dicts (`days`, `hours`), and enum-like options (`cloud`, `resource`, `operation_type`) at the CLI/config boundary before any cloud API call runs *(from Skill 3 Patterns 1 & 2)*.
- **Rule 3.3 (`import-linter` & `__all__` Hygiene)**: Define explicit `__all__` exports in package `__init__.py` files and obey `import-linter` contracts: `crc.policy` must never import `crc.{aws,azu,gcp,oci}` or cloud SDKs, and provider packages must not cross-import one another.

#### Section 4: Error Handling and `CLEANUP_SAFETY.md` Invariants *(from Skills 3 & 5, adapted to CRC)*
- **Rule 4.1 (Specific Exceptions & Chaining)**: Raise specific builtin or domain exceptions (`ValueError`, `TypeError`, `RuntimeError`) with actionable context messages (what failed, resource ID/region, why) and chain underlying SDK errors with `raise ... from e` *(from Skill 3 Patterns 4 & 6)*.
- **Rule 4.2 (Circuit Breakers & List/Auth Failures Must Raise)**: Never wrap opt-in circuit breakers (such as hitting `aws` + `disk` without explicit `--cloud aws --resource disk`) or region-list / VM-list authentication failures (`describe_regions`, Azure `SpotVM` list) in catch-all batch loops; these must raise and fail the run immediately (`CLEANUP_SAFETY.md`).
- **Rule 4.3 (Fail-Closed on Uncertain Telemetry or Bad Retention Tags)**: When CloudWatch `GetMetricData` is incomplete (`PartialData` on final page, missing pages, auth failure) or when a resource's custom age tag is empty, malformed, zero, or overflows (`Service.validated_retention_age`), fail closed by skipping and keeping the resource—never fail open.
- **Rule 4.4 (Scoped Per-Resource Isolation in Delete Loops)**: Where `CLEANUP_SAFETY.md` specifies per-resource fault isolation (e.g., per-volume delete errors inside a region in `AWS_Disk.delete` or per-VM delete errors in Azure `SpotVM.delete`), catch specific SDK exceptions (`ClientError`, `BotoCoreError`, cloud SDK errors), log the resource ID and error, record `_had_errors`, and continue without corrupting `disks_to_delete` / Slack / Influx reporting. Never use silent `except Exception: pass`.
- **Rule 4.5 (Single-Layer Retry & Destructive Ordering)**: Do not layer application `@retry` decorators on top of cloud SDKs that already retry (`botocore`, Azure SDK, OCI SDK) *(from Skill 5 `Double Retry`)*. Preserve strict destructive ordering (e.g., AWS Spot: tag `DeleteOnTermination=false` volumes $\rightarrow$ cancel request $\rightarrow$ terminate instance $\rightarrow$ wait for EBS `available` $\rightarrow$ delete volumes; abort termination if cancel fails, and clear `crc_leftover_of` / `crc_leftover_tag_*` tags if cancel/terminate fails).

#### Section 5: Unit Testing & Cloud SDK Mocking *(from Skills 2 & 5 + CRC Gaps)*
- **Rule 5.1 (Offline Mocked Unit Tests)**: All safety invariants, age/tag policy edge cases, fail-closed branches, and operation sequences must be tested with `pytest` and `unittest.mock` (`Mock`, `MagicMock`, `patch`, `call`) without live cloud credentials.
- **Rule 5.2 (Parametrized Edge-Case & Error-Path Coverage)**: Use `@pytest.mark.parametrize` for tag/age/regex matrix cases and `pytest.raises(ExpectedError, match=...)` for opt-in circuit breakers and invalid inputs. Test both happy paths and failure/fail-closed paths *(from Skill 2 Patterns 3 & 5 and Skill 5 `Only Testing Happy Paths`)*.
- **Rule 5.3 (Test Isolation)**: Use function-scoped fixtures, `monkeypatch` for environment variables, and `tmp_path` for temporary files. Avoid `autouse=True` session fixtures or shared mutable state across tests *(from Skill 2 Patterns 7 & 8)*.

## 6. Security Concerns with Installing Third-Party Skill Content

Evaluating and installing third-party agent skills from marketplaces (`mcpmarket.com`) or external GitHub repositories carries several concrete security risks for an infrastructure cleanup repository:

1. **Mutable Upstream References (`main` branch rug-pulls)**:
   - On MCP Market, Skills 3, 4, and 5 link directly to `https://github.com/wshobson/agents/tree/main/...` (a floating branch reference), whereas Skills 1 and 2 link to immutable commit SHAs (`1e8c7e79...` and `9d486d08...`). If an agent environment dynamically fetches or syncs skills from `main` or via a third-party marketplace CLI, a compromised upstream maintainer account or malicious PR to the upstream repo can silently alter `SKILL.md` after initial review.
2. **Direct & Indirect Prompt Injection in High-Privilege Context**:
   - Agent skills (`SKILL.md` and linked markdown files) are loaded directly into the agent's trusted instruction context. Malicious or compromised third-party skills can embed hidden directives (e.g., via HTML comments, zero-width/Unicode tag characters, or imperative rules under `## Instructions`) that instruct the coding agent to exfiltrate environment secrets (`AWS_SECRET_ACCESS_KEY`, `AWS_ACCESS_KEY_ID`, `AZURE_CREDENTIALS_CLIENT_SECRET`, `GOOGLE_APPLICATION_CREDENTIALS`, `SLACK_BOT_TOKEN`, `INFLUXDB_TOKEN`), weaken `--dry_run` / `--exception_tags` checks, or execute arbitrary shell commands during test runs.
3. **Uninspected Transitive Companion Files (`resources/` and `references/`)**:
   - Three of the five evaluated skills (Skills 2, 3, and 4) use a short top-level `SKILL.md` that instructs the agent to open secondary files (`resources/implementation-playbook.md` at 906 lines; `references/details.md` at 171 and 237 lines). Reviewing only the top-level `SKILL.md` leaves over 1,300 lines of transitive prompt instructions unvetted.
4. **Supply-Chain & Dependency Confusion via Hallucinated/Unapproved Packages**:
   - Skills 2, 3, 4, and 5 instruct agents to import or `pip install` external packages not used by CRC (`pydantic`, `pydantic-settings`, `httpx`, `sqlalchemy`, `hypothesis`, `pytest-cov`, `tenacity`). If an autonomous coding agent has shell access and follows skill instructions to `pip install` packages that are not pinned or vetted in `requirements.txt`, it widens the supply-chain attack surface in developer and Jenkins environments.
5. **Destructive Operational Drift via Unsafe Blanket Patterns**:
   - Even without malicious intent, generic third-party skills encode assumptions for web CRUD apps (such as catching all per-item exceptions in batches or defaulting missing filters) that can cause catastrophic resource deletion in a cloud cleanup tool if applied over domain-specific safety rules.

### Required Mitigations for CRC

- **Vendor and commit in-repo**: Never use live marketplace sync tools or fetch remote skill URLs at agent runtime. Commit the curated, merged skill markdown directly into this repository under version control.
- **Strip transitive external references and unapproved imports**: Inline only the verified rules we keep; remove all references to external URLs, companion files, and unapproved third-party packages.
- **Enforce CODEOWNERS / PR review on skill files**: Treat any modification to agent skill files with the same review scrutiny as changes to `CLEANUP_SAFETY.md` or `crc/`.
