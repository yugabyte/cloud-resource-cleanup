## 2. Fail-open semantics (`SlackNotifier.fail_open = False`, `InfluxNotifier.fail_open = True`)

Verified fail-open behaviour on every path through `crc.py` today and through
`crc.core.engine.run` later:

- On `main:crc.py`, every `slack_client.chat_postMessage` call (`:277`, `:303`,
  `:346`, `:363`, `:383`, `:402`, `:413`, `:431`, `:448`, `:465`, `:484`, `:504`,
  `:605`, `:636`, `:663`) is individually wrapped in
  `try ... except Exception as e: print(f"Failed to send message '{...}' to Slack channel '{...}': {e}")`.
- In `SlackNotifier`, both `chat_postMessage` sites (`SlackNotifier.post` at
  `crc/notify/slack.py:239-247` and `SlackNotifier._ping_user` at
  `crc/notify/slack.py:308-311`) wrap the call (and `"#" + self.channel`) in the
  same `try ... except Exception as e: print(...)`. Therefore, a
  `chat_postMessage` failure never raises out of `SlackNotifier.send`: it prints
  the exact error message, continues to any remaining Slack messages in the same
  report (e.g. Azure VM -> NIC, Spot Request -> Disk, or subsequent owners in
  `ping_owners`), and returns normally so `crc.core.engine.run` proceeds to
  `InfluxNotifier.send` without raising or logging an extra `logger.error`.
- Conversely, the two Slack errors that are *not* inside a `try` on `main:crc.py`
  — `conversations_open` / `response["channel"]["id"]` in `_ping_user` (`BUG-042`)
  and iterating `user_groups = "not_found"` in `_ping_in_channel` when
  `usergroups_list` failed (`BUG-041`) — propagate out of `SlackNotifier.send`.
  Because `SlackNotifier.fail_open` is `False`, `crc.core.engine._notify`
  re-raises them before `InfluxNotifier` runs, matching `main:crc.py:920-924`.
  (If `SlackNotifier.fail_open` were `True`, `engine._notify` would swallow
  `BUG-041` and `BUG-042` and continue to InfluxDB, diverging from `main`.)

## Round 2 (Opus)

Scope: `git diff 61846b5..777afb6` (the rung and round 1's fixes), compared with
`git show main:crc.py` and `git show main:crc/notifications.py`, plus an ad hoc probe that ran
the legacy oracle and `crc.py` side by side on non-list inputs.

### Round 1 fixes assessment

- `CRC.get_msg` `len(operated_list)` first (`crc.py:286`): correct. `None` again raises
  `object of type 'NoneType' has no len()` as on `main:crc.py:324`, and the `_OPERATIONS`
  lookup still comes after it. No other behaviour changed.
- Parity test extensions (`tests/test_notify_parity.py`): every new test compares
  `(slack calls, influx calls, stdout, error)` from the oracle with the new code through
  `assert_same`, and the quirk tests also assert concrete values (`BUG-028`, `BUG-034`,
  `BUG-041`, `BUG-042` texts). No test was removed, skipped or loosened. The ids of the
  `test_get_msg_matches_legacy` parameters changed only by adding `None`.
- The round 1 citations I relied on are correct on `main`: `get_user_groups_list` returns
  `"not_found"` at `crc.py:228`, groups are fetched at `:245` and iterated at `:258-259`,
  `conversations_open` / `channel_id` at `:296-299`, the `try` at `:301`.

### BLOCKING (fixed)

1. **`CRC.ping_on_slack` changed call order and error text for a bad `operated_list`**
   (`crc.py:257-271`, `tests/test_notify_parity.py:308-327`). On `main:crc.py:243-246`,
   `get_user_groups_list()` runs first and then `len()` of every value (the dead sum,
   `BUG-033`), before any owner is pinged. Round 1 built the `Report` first, and `Report`
   calls `.items()` and `tuple(ids)`. So a `None` value raised `'NoneType' object is not
   iterable` instead of `object of type 'NoneType' has no len()`, a non-dict raised `no
   attribute 'items'` instead of `'keys'`, and `usergroups_list` was never called. This is
   the same kind of error-text divergence that round 1 fixed in `get_msg`. Fix:
   `ping_on_slack` fetches the groups, measures every value as `main` does, then hands the
   cached groups to `ping_owners`, so `usergroups_list` is still called exactly once. The
   new test `test_ping_on_slack_bad_input_matches_legacy` covers a `None` value, an `int`
   value and a list. It asserts the exact error, that `usergroups_list` was the only call,
   and that nothing was printed. All 3 cases fail without the fix.

### NIT (left)

- Non-list id containers are rendered differently. `Section` stores `tuple(ids)` and
  `get_msg` / `format_owner_ping` print `list(...)`. A tuple therefore shows as `['a']`
  instead of `('a',)`, a dict shows its key list instead of the dict, and a string would be
  split into characters (`crc/core/report.py:44`, `:134`, `:178`, `:209` vs
  `main:crc.py:324-329`, `:266-290`). No product path hits this: every `get_deleted`,
  `get_stopped`, `get_deleted_nic` and `volumes_to_delete` in `crc/aws|azu|gcp|oci` starts
  as `[]` and stays a list, and the only dict (disk with `slack_user_label`) is routed to
  `ping_on_slack`, whose values are lists. The `crc.core.report` pure contract would have
  to keep raw objects to change this, so I left it. A cleaner rung that returns a non-list
  must check it.
- `CRC.get_msg` / `ping_on_slack` raise `KeyError` for an operation word other than
  `Deleted` / `Stopped` where `main` formatted it (already listed under the R3 open issues
  in `STATUS.md`; unreachable).
- `InfluxNotifier._emit` evaluates `str(resources)` and `len(resources)` before
  `Point(cloud)`, while `main:crc.py:529-534` builds the `Point` first. The order only
  matters if both fail, and the catch-all prints either error in the same format.
- R3 review section 2 cites `SlackNotifier.post` as `crc/notify/slack.py:239-247`; the
  method starts at `:233` (the `try` is at `:239`). Not edited.
- New quirks in the moved code, both present on `main`: `BUG-043` (`human_readable_timedelta`
  padding) and `BUG-044` (`send_slack_message` attempts vs retries, double logging) in
  `docs/refactor/BUGS.md` (44 rows).

  standard library; `crc.core` does not import `crc.notify`; 5 import-linter contracts kept.
  `crc/notify/README.md` has the four ARCH-002 sections and matches `__all__`.
- No cleaner, age, policy or `CLEANUP_SAFETY.md` invariant code changed. Only notification

- Typing: `Any` only at the SDK edges (`SlackClient`, `InfluxClient`, lookup results); the
  two `# noqa: E722` are justified (BUG-033).
